### Findings that change the plan
1. **The mover jumps the new unit's queue unless we decide otherwise.** Between entry and the date the top-up has not happened. A planned mover from a low-overtime unit is listed in the new unit at their own hours, so for any shift after the move date they are at or near the top of that unit's call order, ahead of people the top-up rule exists to protect. A posting made in that window freezes those hours. This is the handover's open question 1, and it is bigger than it looked: it is not only "which number is shown", it decides who is offered and who is charged. Decision 1 has three options, including a new one (not listed in the new unit until the move is applied).
2. **The crew has to be dated at entry, not on the day.** "Scheduled" and the rest rule come from `CrewOn(emp, date)`, which reads the crew history. If the planned row only holds the new crew, lists for shifts after the move show the person in the new unit on their OLD crew's schedule. v24 already allows a future-dated crew row. So a planned move with a crew change writes that crew row at entry, and Cancel has to undo it (a second row, same date, old crew: of two rows with the same date the later one wins, modPeople.bas:133). Decision 6.
3. **Two places read a unit code without `LoadEligible`** and would miss a planned move: `RosterLookup` for an out-of-department award (modPostings.bas:1458) and `ReopenPosting`'s check for people who no longer hold the code (modPostings.bas:1882). Both get the dated lookup with the posting's shift date.
4. **`ExemptFromOpenPostings` marks can't be told apart today.** A cancel must remove only this move's marks, not an "Exempt - left" or another move's. The mark carries the planned move's ID.
5. **`SaveUnitMove` shows boxes and saves.** Run from the open it needs a `batch` argument: no pay-period confirm, no save, failure text returned instead of shown. It is a Function, so an optional argument is safe (it is not on the Alt+F8 list). The verify step inside it is untouched.
6. **`PeopleOnOpen` swallows errors and leaves early when there is no Crew History table.** The apply step is a separate routine called after the crew work with its own handler, so a crew problem cannot hide a due move and the other way round.
7. **A due move is applied only by an admin open.** If a non-admin opens the file first on the day, lists already treat the person as moved (by date) but the top-up is not there yet. With every supervisor an admin at go-live this is a small window. Needs Attention shows the row as "DUE - not applied" and `ApplyPlannedMoves` can be run by hand.
8. **Who's next reuses one list for 14 days** (modPublish.bas:500). It loads per date only when a planned move falls inside the window; otherwise the publish is unchanged and no slower.
9. **The year end.** A move planned in December for January is applied after the rollover, when hours are zero for everyone, so the top-up is small or nothing. The table survives the rollover untouched (nothing in modRollover reads it). No code, but the install note says it.
10. **SmokeTest gets step 14 before SmokeTest has ever run.** The step is written; whether it works is known only after v24.2 is installed. The brief holds the final zip until then.
11. **Size.** About 350 new lines in modPeople, 1 changed line in `LoadEligible`, about 60 in modCalendar, 30 in modPostings, 15 in modPublish, 40 in frmEmployee, plus tests. Smaller than v24.2. It needs its own review round because it changes who is on a call list.

### Decisions (multiple choice)
| # | Question | Options, recommended first |
|---|---|---|
| 1 | The mover on new-unit lists for shifts after the date, before the top-up | **Listed at the hours they would have after the top-up** (highest grade <= 2 total in that unit today, never below their own; an estimate, worked out again on the day) / listed at current hours (the brief's default) / not listed in the new unit until the move is applied |
| 2 | Changing a planned move | **Cancel and re-enter** / an Edit button |
| 3 | Rename, Remove, second move while one is planned | **Rename follows it, Remove cancels it, a second move is refused until the first is cancelled** / any of the three cancels it with a note |
| 4 | Top-up hours when it is applied | **As of the effective date** (as a back-dated move does today) / as of the day it is applied |
| 5 | The members' file | **Who's next follows the move by date; the roster table stays on today's units** / also show "moving to X on <date>" on the person's card / show nothing until the day (Who's next then disagrees with the master for those dates) |
| 6 | A crew change that comes with the move | **Written at entry as a future-dated crew row** (lists are right from the start; Cancel undoes it) / changed only on the day (lists for later shifts use the old crew's schedule until then) |

### Answers (Graeme, Oct 12, 2026)
| # | Answer |
|---|---|
| 1 | **Hours after the top-up.** On a list for a shift on or after the date, a planned mover's Total is the highest grade <= 2 total among the others on that unit's list, never below their own. An estimate for order only; the real top-up is worked out on the day. One pure function (`PlannedListHours`), applied inside `LoadEligible` before the sort, with cases |
| 2 | **Cancel and re-enter.** No Edit |
| 3 | **Rename follows it, Remove cancels it, a second move is refused** until the first is cancelled |
| 4 | **As of the effective date** |
| 5 | **Who's next only.** The roster table and the card stay on today's units |
| 6 | **Crew dated at entry**; Cancel puts the old crew back |

### The gate
Every release since v24.1 has been written without being run. v24.2 (1,700 new lines: SmokeTest, the updater, 40 error handlers) is still uninstalled, and v24.3 will sit on top of it. Pulling more work forward makes the unrun stack deeper, and a fault found at install gets harder to place with each layer.

**So: nothing is built more than one release ahead of what has run in Excel.** v24.3 can be built now. The next release after it starts when v24.2's SmokeTest has passed on a practice copy. The Payroll # key starts only when v24.2 has done at least one Kronos import on the copy, because column A has to be filled before anything can be keyed on it.
