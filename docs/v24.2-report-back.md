Member View then stops with "the template is older than this roster" and writes nothing, so the published file that was opened was still the old one. **To see M2 today, on the desktop copy (no new code needed):** open the TEMPLATE, Alt+F8 > `BuildMemberTemplate` > OK, wait for "Template built (Members M2 ...)", Ctrl+S, close it. The fix for v24.2 makes this impossible to miss, and is not large:

- **`UpdateMemberTemplate`** (item 1) does the whole of install part B in one click, so no step can be missed.
- **A layout stamp.** `BuildMemberTemplate` writes the version that built the sheets into `dLists`. `MemberRefreshAll` compares it with `MEM_VERSION`; on a mismatch Home shows one red line: "Code is M2, sheets were built by M1: run BuildMemberTemplate". The publish reads the same stamp and `MEM_VERSION` and refuses a mismatch with that sentence.
- **No more silent redraw.** A failed redraw writes "This file didn't finish loading (step, error). Tell your supervisor." on Home. No pop-up for members.
- **The publish message** ends with the members' version it wrote and the full path, and says so when a file of the same name also sits in the old folder.

## Findings that change the plan

### Install kit
1. **Replace code in place instead of remove + import.** The brief says remove each component and import the file. In VBA a removed component is not really gone until the running macro ends, so an import of the same name straight after it arrives as `modPostings1`. The dependable way is to keep the component and swap its text (`CodeModule.DeleteLines`, then add the file's text with its `Attribute VB_Name` line taken off). New modules are imported; existing ones, forms and ThisWorkbook are replaced in place. Same result, no duplicate-name risk. Decision 4.
2. **The first v24.2 install has one manual step.** A v24.1 workbook has no updater. Import `modUpdater.bas` by hand (one File > Import), then run `UpdateFromFolder`. From v24.3 on it is one click.
3. **Swapping code resets the workbook's memory.** Changing modules while Excel is running clears every module-level variable, including "admin view is on". If the file were saved in that state, the save would skip switching to the restricted view. The updater therefore ends by re-applying the view through the NEW code, and its last message is: Debug > Compile, SystemCheck, save, close, reopen.
4. **The updater calls nothing in the modules it replaces.** It keeps its own admin test, its own backup (`SaveCopyAs`) and sets the no-save flag by writing the same hidden name the roster reads. `SystemCheck` and `ApplyView` are run by name at the end, so they bind to the new code.
5. **The updater is the one piece that reviews protect least.** It cannot be tried here, and it edits code. So: it backs up first, it has a "check only" run that lists what it would replace and changes nothing (`CheckUpdateFolder`), any failure blocks the save, the manual steps stay in every install note, and its first use is on a COPY. v25 plans a VBA project password: the updater will then need the project unlocked first, and will say so.
6. **`BuildMemberTemplate` cannot take an optional "quiet" argument.** A macro with any argument drops out of the Alt+F8 list, and the install note tells Graeme to find it there. It stays as it is and calls a new inner routine; the updater calls the inner one. The same applies to every button macro.
7. **Nearly every form entry point has no error handler.** No form has an `On Error GoTo`; six of the ten workbook events have none; the other four swallow errors silently. Adding `ReportError` to the entry points therefore touches all nine forms and ThisWorkbook: every `FORM_RELEASES` entry and `THISWB_RELEASE` move to v24.2. With the updater that costs nothing at install; by hand it is ten pastes.
7a. **There is no shared "make an admin sheet with a table" helper**; each module has its own copy. The Error Log follows the Grade Log's. Admin-only sheets are hidden by one list in `ApplyView` (modOvertimeEntry.bas:996); the Error Log sheet is left OUT of that list so it stays very hidden even in the admin view, and `ShowErrorLog` shows it on request.
8. **`Workbook_Open` hides errors today.** One `On Error Resume Next` covers the whole open. Each step will log a failure to the Error Log and carry on, so a broken on-open step shows on Needs Attention instead of vanishing.

8a. **Tried on Oct 12, and it crashed Excel.** Graeme asked for v24.1 as a one-button install, so the updater was built early (`modules/modUpdater.bas`, v1.1, two review rounds, checkers clean) and run on a v24 roster. After OK on "Update now?" Excel raised an exception and restarted with a recovered copy. The roster on disk was not touched (the updater never saves, and a backup was taken first). **Cause, as far as it can be told without running it: the updater sat inside the workbook whose code it was rewriting.** Both reviews had flagged this as a risk that could not be tested here.
   **Change of design for v24.2:** the updater lives in its own small workbook (`Roster Updater.xlsm`: a blank workbook with `modUpdater` imported, made once). The roster is open but none of its code is running while its modules are swapped; the save block, rollback, `UpdateFinished` and `UpdateDrop` carry over. The in-roster version is not to be used again. v24.1 goes in by hand from `INSTALL-v24.1.md`.
   **Also seen in M2 testing the same day:** the Find me arrow on the members' Home sheet is hidden behind the button beside it (an old layout bug); a members' file filled by an older roster shows wrong figures instead of a warning (v24 roster + M2 file read every unit from the wrong column); Excel's events were found switched off in the session once, which stops the members' file reacting to a picked name.

### SmokeTest
9. **"Never saves" needs one switch, not arguments.** `SaveIfWritable` is called deep inside `SaveNewHire`, `SaveUnitMove`, `CreatePostingFrom`, `SaveSickCall`, `SaveSwitch` and others. A single flag in modOvertimeEntry (set only by SmokeTest, only on a COPY-named file) makes `SaveIfWritable` do nothing and `ConfirmPeriod` answer yes. At the end SmokeTest sets the no-save block, so the copy closes without saving.
10. **Posting confirms are in the module.** `CreatePostingFrom` (confirm + result box), `SubmitAward` (up to four confirms, the result box, and an Outlook draft through `EmailAward`), `EarlyOK` (a posting made today always asks "it doesn't close until ..."), `SubmitCancel`. These get an optional `quiet` argument that skips the pop-ups AND the email. Their defaults keep today's behaviour.
11. **Some rules exist only inside forms**, so a test that calls the module functions never runs them: the shift-switch eligibility stops and payback checks (frmShiftSwitch), "vacation and personal days on scheduled shifts only" with its trim offer (frmTimeOff), the already-booked-sick check and the outcome note (frmSickCall). Moving them is the brief's own principle (one copy, in a module) but it is more than v24.2 was sized for. Decision 5.
12. **A crew change with a date has no pop-up-free entry point.** `ReconcileCrew` is private and asks through an input box. SmokeTest will write column E with events off and call `AddCrewRow`, which is exactly what convention 5 in CLAUDE.md prescribes.
13a. **The calendar asks "which line?" through an input box.** An accepted call-out (`CalendarAddAccepted`) and an award on a posting with no live calendar line (`CalendarOutcome`) both reach `CalendarPlace`, which prompts when it has no slot. Creating a posting already has a way to pass the slot (`gCalPostKey`). The quiet path gives the other two the same: under the SmokeTest switch they take a new line without asking.
13b. **The undo steps have no callable core.** `VoidEntry`, `AddAdjustment`, `VoidSwitch`, `VoidAbsence` and `ReopenPosting` each ask for the ID and the reason through input boxes and do the work inline. "Void everything it logged" needs `VoidEntry`, `VoidSwitch` and `VoidAbsence` split into the asking part (unchanged for the buttons) and a function that takes the ID and the reason. One copy of the work, two callers.
13. **Failure pop-ups stay.** Validation and "did NOT verify" boxes still appear if a step fails. That is wanted: the run stops there and the step is reported.

### Planned unit moves
14. **The future-date refusal is one line** in `ComputeUnitMove` (modPeople.bas:1276). `SaveUnitMove` has no date check of its own and takes no backup. A planned move is entered through a new `SavePlannedMove`; `SaveUnitMove` stays the only code that changes the roster, and gets a backup when it is run from the on-open path.
15. **Three callers of `LoadEligible` pass no date** and will not see a planned move: the publish's Who's next (one list per unit, reused for all 14 days, modPublish.bas:458), and the peer lists for leave return and new hire. Who's next must load per date when a planned move falls inside its 14 days. The peer lists are "as of today" on purpose and stay.
16. **Applying on open happens inside `Workbook_Open`.** `SaveUnitMove` shows a period confirm and saves. The on-open path uses the quiet switch for the confirm, applies every due move, shows one summary, and saves once at the end. A move that fails stays Planned and is listed.
17. **The mover's hours on the new unit's lists before the move.** Between entry and the date the top-up has not happened. A posting created in that window for a shift after the move freezes the mover's CURRENT hours on its list. Decision 6.
18. **This is the largest item and the only one that changes who is on a call list.** It needs its own review round. I recommend the brief's default: install kit first as v24.2, planned moves as v24.3. Decision 2.

### Payroll #
19. **The privacy check does not see numbers.** `PrivateDataIn` (modPublish.bas:730) looks at text cells only. A payroll number that reached a published table as a NUMBER would pass. Fix: any number of 1,000,000 or more in a published table stops the publish (no hours figure is ever that large; dates are a different type). Text is already covered by the 7-digit rule. The numbers are stored on the roster as text, so leading zeros survive and the existing rule also applies.
20. **Column A is forced hidden by `ApplyRosterLayout`** (modUI.bas:554) and `ApplyView` knows nothing about it. Both change: A is shown in the admin view and hidden in the saved view, like phone and email. Header `PAYROLL #` goes in A2, where the other headers are.
21. **The import hard-codes name = column 2, total = column 13.** I cannot see the real sheet. The import will look for a header cell reading "Payroll #" (ignoring case, spaces and punctuation) in the first 10 rows. Found: that column is the number. Not found: the import behaves exactly as today and says "no Payroll # column found". Name and total stay where they are.
22. **The Former sheet has 22 fixed columns.** Payroll # goes on the end as column 23, added once on first use (the Hours History pattern), so existing columns keep their numbers. `BringBack` puts it back on the roster row.
23. **"Number matches, name differs" keeps the middle-initial rule.** "Dobbin,Stephen" against Kronos "Dobbin,Stephen A" is the same person today and stays so. Only a real difference is reported, and that row's Worked hours are then left alone, as the brief says.
24. **IntegrityCheck gains one Check line:** the same Payroll # on two roster rows.

### Small items
25. **Refusals Report range:** `SplitTotals` already takes a first and last period, so from / to is a prompt and two arguments.
26. **PRINT / PUBLISH has one free slot** after Refusals Report; ADMIN is full. "Make a practice copy" goes in the free slot or stays Alt+F8 only.
