## What is slow (as read before the numbers; kept for the record)
`DrawCalendar` (modCalendar, ~270 lines) for a 31-day month with ~40 lines:
- **Slots.** `SlotsFor` is called twice per day per shift (one pass for the row heights, one to write: 4 x 31 = 124 calls) plus 28 from `OpenAhead` for the Needs-attention button. Each call runs `AbsActiveOn` over every absence row (`IsDate` / `CDate` on Variants), then for each absence active that day, in the group and on the shift (`AbsenceOnShift` -> `EmpShiftOn` -> `CrewOn`; a sick call with a booked shift returns early) one full pass over the coverage rows (`CovLive`), and one final pass over the coverage rows for the lines without an absence.
- **Cells.** Every slot is written cell by cell (`WriteSlot`: ~14 property sets x 2 cells), every date cell through `DateCells` with two rich-text `Characters` edits, every row height one at a time, borders per week per day: roughly 3,000 Excel object calls.
- **Notes.** One `ClearComments` + `AddComment` + 8 shape property sets per line (`AddNote`); `LineDetails` builds the text per line (its own coverage scan).
- **Wipe.** `Rows("3:1000").Delete` over a sheet with merges and ~40 comments, then `Clear` / `UnMerge` / `ClearContents`.
- **Controls.** `BuildCalControls` deletes and re-creates 11 controls (9 buttons and 2 drop-downs) every draw (`OpenAhead` inside it).
`DrawNeeds`: ~3,000 cell calls for 50 rows, `SlotsFor` over the range, and `HomeUnitOf` (a roster scan per call: modLeave) per name and per planned move (C7).
Also on the calendar's open path (the Calendar button, admin only, before the draw): `SyncSwitchesToCalendar` re-reads the whole Coverage table once per non-void switch (C5), then `SaveIfWritable` when it added a line; and after the draw, `Done` puts calculation back to automatic (a recalculation) and the screen repaints. Not on the calendar's path but in 4.7's list: `FilterNotFree` / `SwitchPickList` re-read the Shift Switches table per person outside a publish batch (C6; their callers are the call-out and switch pop-ups, postings and the publish).

## Items, in commit order, by the numbers (each its own commit; ONE install, v25.2, at the end - what its testing turns up is batched into v25.2.5, never one install per fix [the numbering rule, Oct 17]; the drawn sheet identical to v25.1.2's apart from the notes rule in item 1)
0. **v25.1.2 - measurement.** Done, installed Oct 17; the numbers above. The Timer lines stay in v25.2 so the "after" is read the same way.
1. **Notes only where action is needed (D-C4 revisited Oct 17 on the numbers: 2.8 of 4.6 s).** `WriteSlot` adds a hover note only on OPEN, NO TAKERS and POSTED lines (a handful per month); covered lines and absences get none, their details stay on double-click > "Details..." (`CalMenuDetails`, already there) and "What's on this day". `AddNote` itself made cheaper: no `ClearComments` on rows the wipe just made, the shape's font set once through `TextFrame.Characters.Font` and the bold title in one call. Needs Attention: `NARows` keeps its notes on the open-line rows (the A: / C: keys) as before. Expected: notes 2.8 -> about 0.2 s.
2. **Page setup once.** The `PageSetup` block (0.6 s, the same values every draw) runs only when the print area's last row changed (kept in CalMap Z17) or the sheet was just made; `Application.PrintCommunication` stays as it is. Expected 0.6 -> 0.0.
3. **Cells in one pass.** The week block's left / right texts, keys and date texts built in 2-D arrays and written with one `.Value =` per block (the texts carry the same leading apostrophe the cell-by-cell writer gave them, so names never turn into dates); row heights through two `Union` ranges (date rows 38, slot rows 17); formats by class through `Union` ranges per class (open, posted, covered, NCN, left text per type colour, out-of-month fill, day fill, night fill, weekend / today); the date cells' rich text (`Characters`) stays per cell; borders per week stay. The wipe becomes `ClearContents` + `ClearFormats` + `UnMerge` + `ClearComments` on the used range instead of `Rows.Delete` when that is faster (measured). Expected cells 0.7 + wipe 0.3 -> about 0.4.
4. **Needs Attention rows (1.0 s for 59 rows).** `NARows` writes each section as one array and formats by class, as item 3; name -> home unit cached in `LoadCache` and read through `HomeUnitCached` by the two Needs Attention callers (`HomeUnitOf` in modLeave stays as it is for everyone else; C7: a roster scan per name today); the tiles (`NATile`, 0.3 s) left as they are. Expected 1.4 -> about 0.6 s.
5. **Proof.** `DrawCalendarLegacy` (the v25.1.2 routine, copied) stays for one release as a Public macro (the hand fallback); SmokeTest step 19 draws the month of the test postings, in the test unit's group, both ways and compares values, fills, font names / colours / sizes / bold / italic, merges, row heights, the CalMap keys, and the comment texts on the OPEN / NO TAKERS / POSTED lines (the only ones both routines write), failing on the first difference; `DrawNeeds` the same way with `DrawNeedsLegacy` (step 20). The two legacy routines and the two steps go in the release after. `DrawCalendar` split into a builder (arrays) and a writer.

Dropped on the numbers (were items in the Oct 17 morning draft): slots once per day + typed caches (`SlotsFor` is 0.0 s), controls once (0.0 s), the switch sync Dictionary (0.0 s), the day-only redraw (a full draw near 1 s does not need it; the riskiest item). Not in v25.2: C6 (`FilterNotFree` / `SwitchPickList` batches: the pop-ups, not the calendar; a later bundle), the relock + recalc 0.4 s at Done (two `ProtectSheet`s and the calculation mode going back to automatic: left alone), any rule change (none is touched; `tests/` and SelfTest stay), the Desk view, the Payroll # key (v25.3), reports (v26).

**Target:** Calendar 4.6 -> under 1.5 s on the same month (notes 0.2, page 0, cells + wipe 0.4, header 0.1, caches 0.1, relock + recalc 0.4); Needs Attention 1.4 -> under 0.6 s.
