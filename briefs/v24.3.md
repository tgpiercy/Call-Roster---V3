## The rule in one paragraph
Employee > Move to unit accepts a future date. Nothing on the roster changes. One row goes into `tblPlannedMoves`. From then on, every list built **for a shift on or after the date** treats the person as moved: off the old unit's list, on the new unit's list with the planned grade code. Lists for shifts before the date are unchanged. On the first admin open on or after the date the move is applied through `SaveUnitMove` (codes, Home Unit, Grade Log, the `UM-` top-up), and the row becomes Applied.

## 1. The table and the pure rule
Sheet `Planned Moves` (admin only, in `ApplyView`'s admin list, never published), table `tblPlannedMoves`, made on first use the way `FormerTable(create)` is. No one-time macro.

| Column | Notes |
|---|---|
| ID | `PM-0001`, next = highest in the table + 1 (rows are never removed) |
| Employee | name, as on the roster |
| New Unit | |
| Grade Code | the code they will hold in the new unit |
| Codes To Clear | units, `|` between them |
| New Crew | blank = no change |
| Old Crew | what column E held at entry (only when New Crew is set; Cancel needs it) |
| Effective From | date |
| Status | `Planned` / `Applied` / `Cancelled` |
| Entered By, Entered On | |
| Closed On, Note | when it was applied or cancelled, and why |

Pure rule, in modPeople beside `CrewOnCore`, mirrored in `tests/rules.py`:

`PlannedCodeCore(plans, emp, unit, d, rosterCode) As String`
- No `Planned` row for `emp` with Effective From <= `d`: returns `rosterCode`.
- `unit` = that row's New Unit: returns its Grade Code.
- `unit` is in that row's Codes To Clear: returns `""`.
- Any other unit: returns `rosterCode`.

Live wrapper `UnitCodeOn(emp, unit, d, rosterCode)` with a cached copy of the table (the `EnsureHist` / `ResetCrewCache` pattern; `AfterPeopleChange` clears it). When the table has no `Planned` row the wrapper returns `rosterCode` at once, so a roster with no planned moves costs nothing.

## 2. Employee pop-up
- `ComputeUnitMove` gets `Optional ByVal allowFuture As Boolean = False`. With it, a future date is accepted and the result is a **preview**: the summary starts "PLANNED for <date>" and ends "Hours are worked out again on the day." Every other caller keeps today's refusal.
- `SaveMove` in frmEmployee: date after today -> `SavePlannedMove`; today or earlier -> `SaveUnitMove`, unchanged.
- `SavePlannedMove(emp, newUnit, gradeCode, clearUnits, newCrew, eff, report)` in modPeople: admin, writable, the person is on the roster once, the unit and code are given, the date is after today, there is no other `Planned` row for that person (item 6). Then: backup (`PeopleBackup`), write the row, mark the old units' open postings dated on or after the move as `Exempt - moves <date> (PM-0007)` (`ExemptFromOpenPostings`), `AfterPeopleChange`, save. The roster's code columns and Home Unit are **not** touched; the before / after totals check must show no change at all.
- The confirm says, in plain words: nothing changes on the roster today; from <date> they are called in <new unit> and not in <old unit>; the move is applied the first time an admin opens the file on or after <date>; Needs Attention > Planned moves cancels it.
- Crew with a planned move: see decision 6 in the report-back.

## 3. Lists by date
- `LoadEligible`: the line `code = Trim$(SafeStr(v(i, dc)))` becomes a call to `UnitCodeOn(nm, dept, <date>, code)` where the date is `asOf`, or today when `asOf` is left out. That one change covers the call-out pop-up, posting lists, `EligibleCount`, `OutsideCandidates`, the printed call-out roster, the switch pick list and SmokeTest, which all pass a date already.
- A person with no name on the old unit and a planned code in the new one is picked up because the test is on the code AFTER the overlay.
- Two places read a unit code straight from the roster and must use `UnitCodeOn` with the posting's shift date: `RosterLookup` (out-of-department award, modPostings) and `ReopenPosting`'s "no longer holds a code in this unit" check.
- Not changed, on purpose: the leave-return and new-hire peer lists and `ComputeUnitMove`'s own peer list ("as of today"); `Sort_Hours_Dept` (a display sort); `BuildRoster` in the publish (today's codes).
- The mover's **hours** on a new-unit list before the top-up: decision 1.

## 4. Apply on open
- `PeopleOnOpen` (already `OpenStep 6`) calls a new `ApplyDuePlannedMoves` after the crew work. No change to ThisWorkbook.
- Admin, writable, not while `NoSave()`. Nothing due: returns at once, silently.
- Something due: one backup, then for each due row, oldest first: `ComputeUnitMove` (hours: decision 4), then `SaveUnitMove(..., batch:=True)`. `batch` is a new optional argument that skips the pay-period confirm and the save, and returns its failure text instead of showing a box. Verification inside `SaveUnitMove` is unchanged; a failed verify still sets `MarkNoSave` and stops the loop.
- Success: Status `Applied`, Closed On, the `UM-` ref in Note. The `Exempt - moves ...` marks become `Exempt - moved ...` (same rows, text only).
- Cannot apply (not on the roster, on the roster twice, unit gone): the row stays `Planned`, Note says why, and it is listed in the summary and as a red line on Needs Attention.
- One save at the end, one summary message: applied (name, unit, hours added, ref), not applied (name, reason).
- Also callable by hand: `ApplyPlannedMoves` (Alt+F8, admin), for a move that came due while the file was open.

## 5. Cancel and Needs Attention
- Needs Attention gets a "Planned moves" block: one line per `Planned` row (name, old -> new unit, date, "in N days"); a row past its date is drawn in the open colour with "DUE - not applied". Key `V:<ID>` (letters in use: P A C S B H I M U T J X E D).
- Double-click or right-click: a short menu or prompt offering **Cancel this move** (and **Apply now** when it is due).
- `CancelPlannedMove(id, reason)`: Status `Cancelled`, Closed On, Note; removes ONLY the `Exempt` marks that carry this move's ID on open postings; undoes the crew row if one was written (decision 6); `AfterPeopleChange`; save.
- Editing: decision 2.

## 6. Rename, Remove, a second move
Decision 3 in the report-back. As briefed by default:
- Rename: `tblPlannedMoves` Employee column joins `NameColumns`, so `RenameEverywhere` carries the planned row with every other table.
- Remove: the planned row is cancelled with the note "removed <date>", and the Remove confirm says so.
- A second planned move, or an immediate move, for someone who has a `Planned` row: refused with "Cancel <ID> first".

## 7. Publish, checks, SmokeTest
- `BuildNext` (Who's next): loads one list per unit and reuses it for 14 days. When any `Planned` row's date falls inside those 14 days it loads per date instead; otherwise it behaves exactly as today. What members see of a planned move: decision 5.
- The `Planned Moves` sheet is never published. `PrivateDataIn` is unchanged.
- IntegrityCheck: a Check line for a `Planned` row whose person is not on the roster, whose unit is unknown, or that is more than 3 days past its date; a Note line with the count of planned moves.
- SystemCheck: lists the table and its row count beside Crew History. `ApplyView` hides the sheet in saved copies.
- SmokeTest: a new step after the unit move: plan a move for tomorrow, check the roster row is unchanged, check `LoadEligible(asOf:=tomorrow)` has the person in the new unit and not in the old, check `LoadEligible(asOf:=today)` is unchanged, cancel it, check the exempt marks are gone. Steps become 14.

## Acceptance
- A move dated next week: the roster row, Home Unit, Grade Log and OT Log are unchanged today; totals check shows no difference.
- A posting created today in the new unit for a shift after the date lists the person; one in the old unit for the same shift does not. A posting for a shift before the date is the other way round.
- An open old-unit posting dated after the move shows `Exempt - moves ...` for them and never charges them.
- Opening the file as admin on the date applies the move: codes, Home Unit, one Grade Log entry per code, one `UM-` row if hours are added, Status Applied, one summary.

## Decisions (Graeme, Oct 12, 2026: don't re-ask)
1. **The mover's hours on new-unit lists before the move:** the hours they would have after the top-up. In `LoadEligible`, after the list is filled and before the sort, a planned mover's `TotalHrs` becomes `PlannedListHours(own, others' totals, others' grades)` = the highest total among the others at grade <= `PEER_MAX_GRADE`, never below their own; nobody to match = their own. Pure, mirrored in `rules.py`, with cases. For order only: nothing is logged, and the real top-up is worked out on the day. A posting made in that window freezes this figure on its list, as it freezes everyone's.
2. **Changing a planned move:** cancel and re-enter. No Edit.
3. **Rename** carries the planned row; **Remove** cancels it with a note; **a second move** (planned or immediate) is refused until the first is cancelled.
4. **Top-up hours:** as of the effective date.
5. **Members' file:** Who's next follows the move by date. The roster table and the person's card stay on today's units.
6. **Crew:** a planned move with a crew change writes the crew row at entry, dated the effective date (column E with events off + `AddCrewRow`, convention 5). Cancel adds a row for the old crew on the same date (the later of two same-date rows wins) and puts column E back. On the day `SaveUnitMove` is called with no crew change.

## As built (Oct 13, 2026): where the code differs from the text above
- **Exempt marks keep their text when the move is applied.** They stay `Exempt - moves <date> (PM-000n)`; they are not rewritten to "moved". The person is never charged either way.
- **The `UM-` ref is not copied into the planned row's Note.** The Note says who applied it and the hours added; the ref is on the OT Log row.
- **Cancel does more than item 5 says.** Postings made while the move was waiting keep their frozen lists, so on the new unit's the person is marked `Exempt - move cancelled (PM-000n)`, and the cancel box names the old unit's open postings made without them (and, when the person already held a code in the new unit, that unit's postings listing them at the planned code and hours). Entering the move again, or a later move into that unit, takes the `move cancelled` mark off.
- **No reason is asked for on a cancel** from Needs Attention; the Note records who and when.
- **The estimate is marked.** `EmpRec` carries `RosterHrs` and `EstHrs`; the call-out pop-up and the printed call-out roster show `~`, and a call-out's log row records the real total. A posting's list, and the log rows of its award, keep the posted figure (the estimate): the Overtime Posting sheet, the award pop-up and the members' file show it without a mark. `frmOvertimeEntry` is therefore re-pasted too.
- **SmokeTest step 9 checks list membership by date and the cancel**, not the exempt marks (it has no open old-unit posting to mark).
- **Tests:** 28 cases (`plancode` 22, `planhours` 6); SelfTest 392 in 47 suites.
