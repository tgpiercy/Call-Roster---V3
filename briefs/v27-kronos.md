## 1. The Kronos report, as it really is
One report, **"Employee Transactions and Totals"**, exported to Excel (one sheet, `Report`, 13 columns). Title block, then THREE blocks:

| Rows | Block | Columns (by heading; the letters are the export's) |
|---|---|---|
| 1-6 | Title | row 1 the report name; rows 2-5 a label in A and the value in D: `Time Period :` **`01/11/2026 - 10/17/2026`** (text, m/d/yyyy), `Query :` `Location - Welland Hourly` (or `Welland All`: every pay code and salaried people too), `Executed on :` `10/21/2026 11:56 AM`, `Printed for :` a name; row 6 a Kronos error line in C / E (`[WFM-COMMON-1234] Failed to retrieve some data from the providers ...`: always there, harmless) |
| 7-637 | **Transactions:** (row 7 the word; row 8 the heading) | A `Global ID` (8 digits), D `Employee` ("Last, First"), F `Date` (a REAL date cell), G `Day`, H `Pay Code`, I `Earnings Amount`, J `Hours`, K `Wages`, L `Edited By` (a name, on 330 of 629 rows), M `DataSource` (`Timecard Editor`). **These are timecard EDITS, not worked time:** 435 of the 629 rows carry NEGATIVE hours (a reversal), the block nets to ~800 h for 58 people over nine months, and DBLTIME nets to -3 h. |
| 638-1190 | **Totals:** (row 638 the word; row 639 the heading, SHIFTED: A `Global ID`, D `Employee`, F `Pay Code`, G `Earnings Amount`, H `Hours`, I `Wages`) | **one row per person per pay code for the Time Period, no date: the real year-to-date hours** (551 rows, 95 people, ~29,500 h; 37 of the 95 have no row at all in the Transactions block). Equal to the Summary block code for code. |
| 1191-1202 | **Summary Totals:** (row 1192 heading: A `Pay Code`, F `Earnings Amount`, G `Hours`, H `Wages`) | the site's hours per code, one row per code (10) |

Pay codes in the `Welland Hourly` query: `CA OVERTIME`, `CA OT - DT Split`, `CA DBLTIME`, `CA STATWK 2.0`, `CA MIN 4`, `CA CALLIN OT`, `CA LIEU OT`, `CA LIEU DT`, `CA LIEU OT - DT Split`, `CA LIEU ST`. ## 2. The design (Graeme's choice, Oct 21: a one-day snapshot every morning + the cumulative report at each period end)
**One report in two Time Periods; the Totals block is the only source of hours; the daily snapshots build a dated ledger; the period-end cumulative rebuilds H exactly and logs every difference; the Transactions block explains the edits.**
1. **The pull (Graeme's job, no code):** each morning the `Welland Hourly` "Employee Transactions and Totals" report for `Time Period` = yesterday .. yesterday, exported to Excel into `KRONOS_PATH`'s folder; at each pay period's end (and whenever H is in doubt) the same report for Jan 11 .. yesterday into the same folder. The import reads every report file newer than the last import, oldest first, and tells the two apart by the Time Period's length (one day = a snapshot; a range = a cumulative, which must START at the year's Kronos start and END on or after every snapshot already imported, else refused with the reason).
2. **The reader, `KronosReport`** (replaces `TransactionsSheet` / `PivotFromTransactions`; the pivot-sheet reader "Sorted Data Here" is kept one more release as the fall-back and then retired): finds the title's `Time Period` (two m/d/yyyy dates, parsed by hand, never CDate), the `Query`, and the THREE blocks by their heading rows (`Totals:` heading = `Global ID` + `Employee` + `Pay Code` + `Hours` with NO `Date`; `Transactions:` heading = the same plus `Date`), each column by heading. Refused with a plain message when the Totals heading is missing, when the Time Period's end is outside the roster year, or when the Query is not `Welland Hourly` (a `Welland All` file is accepted but every non-roster code is reported - section 2.4). Pure core **`KronosTotalsCore(rows, codes, multipliers)`** -> per person: hours per code, the weighted total, the unknown codes (suite `ktotals`); pure **`TimePeriodCore(text)`** -> from, to (suite `kperiod`).
3. **H** = for each roster person (matched by Payroll # through `PayrollDecision` first, `NameKey` second, as today), **the cumulative's Totals through its end date + the snapshot days after it** (the ledger, 2.6), each as the sum over the ROSTER codes of hours x that code's multiplier, **rounded to a whole number per person after the sum** (`ROUND(..., 0)`, as the workbook does; the ledger keeps the unrounded weighted hours, H and the per-period figures are rounded where shown). **The multiplier table (section 1b, CORRECTED by Graeme Oct 21: the workbook had LIEU OT and LIEU DT swapped):** `OVERTIME` 1.75, `OT - DT Split` 2, **`LIEU OT` 1.5, `LIEU DT` 2**, `LIEU OT - DT Split` 1.5, `LIEU ST` 1, `CALLIN OT` 1.75, `MIN 4` 1.5, `STATWK 2.0` 2 (`DBLTIME` 1 in the workbook, moot: never on an operator); the settings `PREMIUM_CODES` + `PREMIUM_MULTIPLIERS` in modOvertimeEntry hold it, mirrored in `tests/rules.py` (`test_drift` compares). **Consequence:** the first v27 import on the real file changes H for everyone with LIEU OT or LIEU DT hours this year (29 and 11 people on the Oct 21 file; a few hours each, down for LIEU OT, up for LIEU DT): the sanity confirm names each of them with the reason "LIEU weights corrected", the What's New box and the members' file say so. The processing workbook is NOT edited for the section-0 re-import (that fix is about the edit-net, the LIEU correction waits for v27); the acceptance test in section 3 therefore expects exactly those people to change and nobody else. **Roster codes (Graeme, Oct 21):** `OVERTIME`, `OT - DT Split`, `LIEU OT`, `LIEU DT`, `LIEU OT - DT Split`, `LIEU ST`, `CALLIN OT`, `MIN 4`, `STATWK 2.0`. **Not roster codes:** `DBLTIME`, `Uanpproved OT`, `LIEU TKN` ("production operators don't receive that pay code") - a roster person who HAS one is reported by name in the import's message and as an IntegrityCheck Check line ("Kronos code not counted: <code> N h"), never silently counted or silently dropped. People in the report who are not on the roster are counted, not listed (the Welland set is ~95; the roster's operators are a part of it).
4. **The write** (item 11's hardening, now here): `PeopleBackup("kronos")`, `RosterTotalsMap` / `TotalsDifference` on every column but H and G, H written from one array, the sanity flags (anyone whose H FELL, or rose by more than 60 h since the last import, named in a confirm before the write; the first import after the v26.5 defect WILL trip it for everyone - the confirm says why), `MarkNoSave` on failure. Hours History gets its dated snapshot as today (+ the Time Period's end as Data Through). `KronosDataThrough` = the Time Period's end.
5. **The change log, `tblWorkedChanges`** (admin-only sheet `Worked Changes`, never published): When, Payroll #, Employee, Date (the day the hours belong to), Pay Code, Hours before, Hours after, Change, Weighted change, Kind (`day` = a snapshot's new day; `edit` = a cumulative that disagrees with the ledger for a person and code, dated by the Transactions block's `Date` for that person and code inside the window since the last cumulative, with its `Edited By` in the Note, else dated the cumulative's end), Source file, Imported by. A snapshot re-imported for a day already held replaces that day and logs the difference. **This is "the change in hours day to day is logged":** the admin answers "why did Joe's hours move, and who edited the timecard" from the roster. Needs Attention lists `edit` rows dated into a CLOSED pay period until an admin ticks them seen.
6. **The ledger `tblWorkedDays`** (admin-only, never published: Payroll #, Employee, Date, Pay Code, Hours, Weighted hours, Source file, Imported At) = one row per roster person per code per snapshot day. **Per pay period (`tblWorkedPeriods`, `dWorked`, the history report's Worked (Kronos))** = the ledger summed per period (weighted hours), exact from the first snapshot day on; **the periods before that show "not available before <date>"** (Graeme, Oct 21: no backfill), the date = the first snapshot's day, kept as the hidden name `KronosLedgerFrom`. A period-end cumulative does not touch the per-period figures except through the `edit` rows it logs (re-dated into their period when the Transactions block says which day).
7. **The Desk tile "Import now"** (v27 item 2) counts the report files in the folder newer than the last import; the trust strip and the Kronos-stale rule read the new Data Through.
