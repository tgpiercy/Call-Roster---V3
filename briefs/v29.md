### As decided (Oct 27)
- **The members' folder path is STORED IN THE FILE by the move** (a hidden name `MembersFolder`), read by `PublishFolderPath` when set; `PUBLISH_FOLDER` stays the default and every other setting stays a constant. SystemCheck shows the stored path. No January install. (Graeme chose this over a v29.0.1 cutover install and over pointing v29 at P: in December.)
- **The roster drives the move; the reopen is by hand.** `MoveRoster` (admin, Alt+F8 and the admin Desk's FINISH band; never on the Lite Desk): (1) refuses unless the file is saved clean, not stale on disk (`StaleOnDisk`), not `NoSave`, not read-only, a live roster, and nobody else has it open; (2) asks for the new MASTER folder and the new MEMBERS' folder (typed or picked; both must exist and pass a write test); (3) copies the roster through `SaveRestrictedCopy` into the new master folder and the members' template beside it; (4) moves `Signups\` (pending files and `Done\`) and `Requests\` (files and `done\`) from the old members' location to the new members' folder (copy, verify the counts, delete); (5) writes `MembersFolder` into the NEW copy (reopening it, writing, saving, closing is not possible from the old file - so the path is written into the hidden name BEFORE step 3, and cleared again in the old file at step 6); (6) freezes the OLD file: the hidden name `MovedTo` = the new path + date, saved; (7) one box: "Close this file. Open <new path>. Then rename this one 'MOVED - ...' (the runbook has the step)". The new file's first open runs SystemCheck + IntegrityCheck (the Install-panel pattern: both results in one box) and republishes the members' file into the new folder. Steps 3-6 verified: the copy's size and a hash where certutil is available, every moved file counted before and after; any failure stops BEFORE step 6, so the old file stays live.
- **The old copy is frozen two ways:** the `MovedTo` marker makes `OpenChecks` treat it as a frozen copy (a box naming the new path; `IsLiveRoster` False, so no backups, no exports, no requests, no publish; `RequireWritable` refuses), and the runbook renames it `MOVED - <date> - <name>` by hand after the close (the existing frozen-name rule).
- **Rehearsal mode:** on a COPY / DRY RUN-named file `MoveRoster` asks for TEST folders and moves into them, keeping the PRACTICE names and every practice rule (no backups, the publish stays `PRACTICE - ...` beside the moved copy, nothing touches P:). It exercises every step and every new SystemCheck line. Dec 7-11 uses it.
- **SystemCheck gains one line per path** - the master's folder, the members' folder (stored or default), Signups, Requests, Backups (with today's state), Archive, Closed, Scans, the error log file, `KRONOS_PATH`, `REPORT_FOLDER`, `GUIDE_PATH` - each resolved path with reachable / writable (a write test = create and delete `~check.tmp`; "not writable" is a warn line, never a failure of the Install panel step), the members' file present with its age, and after a move: "this file moved from <old> on <date>". The reports-folder line speaks when the P: parent is unreachable too.
- **Rights, the IT ask (G2, by Nov 20):** the members' folder root READ for members; `Signups\` and `Requests\` LIST + READ + WRITE for members (the members' file reads them back); supervisors MODIFY on the whole members' folder (SaveAs of the members' file, MkDir, the `Done\` / `done\` moves); the supervisor-only master folder MODIFY for supervisors, nothing for members.
- **Wording fixed** where "beside the roster / this file" becomes wrong: `modEvidence.bas:161`, :373; `modSignups.bas:208`; `modRequests.bas:112`; `modMember.bas:3112`.
- **Stored absolute paths** (`EV_PATH`, the Closed CSV / PDF) are left as history; IntegrityCheck 15 "Records" gains a Note when a stored path's folder is not the current Closed / Scans folder ("moved on <date>").
- **Known and accepted:** the `~$` lock file, the pre-change copies, Practice and the PDFs "beside the roster" follow the master (right after a split); the Dec 2026 FINAL stays in the OLD master folder (the rollover runs before the cutover; the runbook copies it); the backups' "kept" count starts again in the new folder; a `Dir` on an unreachable share can be slow at open (steps 1, 10, 13 and the Desk's Kronos count) - the runbook's day-before check covers it.
